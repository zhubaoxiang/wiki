## 问题一：continuous_events 带 src_ip 的 count / 列表查询慢（41s）

### 现象

带可选条件 `src_ip = 'xxx'` 的 count 和列表查询执行 **40+ 秒**，页面基本不可用。

### 根因分析

执行计划显示三层问题叠加：

```
Bitmap Index Scan (end_time 范围索引)  → 2,361,719 行候选
Bitmap Heap Scan Recheck              → 剔除 6,678,463
Filter: src_ip = 'xxx'                → 剔除 1,899,958
最终输出                              → 8 行
Heap Blocks: exact=38,443 lossy=559,943
```

1. **src_ip 不在索引里**：索引 `idx_ce_judge_endtime_eventid_new` 只有 judge/end_time/event_id，src_ip 被优化器丢到 Filter 阶段，236 万行候选必须逐行回表比对；
2. **lossy bitmap**：候选集太大，work_mem 放不下 bitmap，退化成 lossy 模式（559,943 个 lossy page），大量 heap 重读；
3. **vdb 磁盘 IO 100% 饱和**：heap 回读被磁盘进一步放大。

**work_mem 调优验证无效**：session 内 `SET work_mem = '256MB'` 后 lossy 完全没变化（559,943 → 559,943），执行时间反而因 IO 波动更慢。结论：work_mem 只影响 bitmap 精度，不能减少回表数据量，候选行数才是根因。

### 优化方案

考虑到 `src_ip` 是**可选条件**（仅页面显式传入时出现），且 `end_time`/`up_bytesall` 等是高频更新字段（复合索引含这些列会带来持续写入开销），最终选择：

```sql
-- 独立单列专用索引，前导列为不更新的等值列
CREATE INDEX CONCURRENTLY idx_ce_src_ip
ON internal_app_bsa_gjk.continuous_events (src_ip);
```

设计要点：
- **前导列 src_ip 不在高频更新字段列表中**，索引维护开销低（主要成本在 INSERT，UPDATE end_time 不触碰该索引）；
- 只有带 src_ip 的查询才会命中，不带该条件的查询不受影响，无需改动主索引；
- 单列即可：查询仍需回表取 end_time/judge_status 等，加 event_id 做 covering 没有收益；
- 开发环境先行验证执行计划（确认走 `Bitmap Index Scan on idx_ce_src_ip`、无 lossy），再上生产。

### 效果

| 指标 | 优化前 | 优化后（生产） |
|------|--------|--------|
| 扫描方式 | Bitmap Heap Scan（end_time 索引） | **Index Scan using idx_ce_src_ip** |
| src_ip 条件位置 | Filter（回表后过滤） | **Index Cond**（索引层过滤） |
| 候选行数 | 2,361,719 | **29** |
| Heap Blocks lossy | 559,943 | 0 |
| 列表查询耗时 | **37 s** | **382 ms**（约 97 倍） |

索引上线后统计确认被稳定使用（idx_scan 持续增长），大小 1003MB。剩余 382ms 主要是 vdb IO 饱和下的回表耗时，属环境瓶颈，暂无进一步优化空间。

## 问题二：CREATE INDEX CONCURRENTLY 被阻塞 18 小时

### 现象

`idx_ce_src_ip` 用 `CONCURRENTLY` 在生产建索引，执行 **18 小时未完成**。

### 排查过程

1. `pg_stat_progress_create_index` / `pg_stat_activity` 显示会话 `state=active`、`wait_event_type=Lock`、`wait_event=virtualxid` —— 卡在等待旧 snapshot 释放阶段；
2. 通过 `backend_xmin` 比对找到一批更老的事务，包括一个跑了 6 天的 `VACUUM ANALYZE netflow_alert_5min`（当时判定为元凶）；
3. **后来发现判定有误**：该 VACUUM 未结束时索引却建成功了。修正认知：
   - **CONCURRENTLY 等待的是持有旧 snapshot 的普通事务**（`idle in transaction`、长 SELECT、未提交的写事务），且**不限本表**——任何表的旧 snapshot 事务都会阻塞；
   - **VACUUM/autovacuum 不以同样方式阻塞 CONCURRENTLY**，不能只看 `backend_xmin` 老就判定为阻塞源。

### 处理结果与沉淀

- 阻塞的普通事务结束后索引自然完成，无需人工干预；
- 验证 `indisvalid=true / indisready=true` 后确认可用；
- **规范沉淀**：CONCURRENTLY 建索引前必须先检查 `pg_stat_activity` 有无长跑普通事务（重点 `idle in transaction`），否则会被持续阻塞。

```sql
-- 建索引前的标准检查
SELECT pid, state, now() - xact_start AS xact_duration, left(query, 100)
FROM pg_stat_activity
WHERE state IN ('active', 'idle in transaction')
  AND xact_start IS NOT NULL
  AND now() - xact_start > interval '5 minutes'
ORDER BY xact_start;
```

### 延伸教训：DROP TRIGGER 锁死表

此前一次 `DROP TRIGGER` 操作也曾长时间等待，期间整张表被锁死。原理：DDL 需要 `ACCESS EXCLUSIVE` 锁，一旦在锁队列等待，**后续所有读写全部排队**，形成级联阻塞。

**规范**：所有 DDL 前设置超时保护：

```sql
SET lock_timeout = '5s';
DROP TRIGGER trigger_name ON table_name;
RESET lock_timeout;
```

## 问题三：continuous_events_tag LIKE '%OpenSSH%' 查询耗时 24 分钟

### 现象

通过标签表定位 `app_type LIKE '%OpenSSH%'` 的 event_id，再回主表过滤时间窗口/状态的 count 查询，执行 **1,444 秒（约 24 分钟）**。

### 根因分析

```
Bitmap Index Scan (tag_name='app_type')  → 15,189,282 行
Bitmap Heap Scan: exact=29,185 lossy=2,388,514
Filter: tag_content LIKE '%OpenSSH%'     → 1,285,676 行
↓
Unique 去重 → 1,285,676 个 event_id
↓
Nested Loop → Index Scan pkey × 1,285,676 次
  Filter (end_time/status/bytes) → 仅 11,698 通过
优化器预估 190,578 vs 实际 1,285,676（低估 6.7 倍）
```

1. **前导通配符 `LIKE '%xxx%'` 无法走 btree 索引**：1500 万行 tag 全部回 heap 逐行匹配；
2. **128 万次 pkey 嵌套循环**：98%+ 的候选 event_id 在时间窗口内根本无匹配，是无效回表；
3. **统计信息严重过期**：`continuous_events_tag` 按天高频 DELETE（分批 1000 条），优化器低估实际行数 6.7 倍；
4. **逻辑冗余**：`tag_content LIKE '%OpenSSH%'` 已隐含 `tag_content IS NOT NULL`，重复的 EXISTS 条件浪费一次 Semi Join。

### 优化方案（按优先级）

| 优先级 | 方案 | 状态 |
|--------|------|------|
| 1 | 删除冗余 EXISTS（IS NOT NULL 被 LIKE 隐含） | 已明确，待落实 |
| 2 | `ANALYZE internal_app_bsa_gjk.continuous_events_tag;` 修正统计信息 | 已明确，待落实 |
| 3 | 改写为 CTE + Hash Join，替代 128 万次嵌套循环（预期 24min → 1-2min） | 已给出 SQL，待验证 |
| 4 | 根治：`pg_trgm` GIN 部分索引 `ON (tag_content gin_trgm_ops) WHERE tag_name='app_type'`，让 `%xxx%` 走索引 | 需评估索引大小与写入成本 |

```sql
-- 方案 3 的改写示例
WITH ssh_events AS (
  SELECT DISTINCT event_id
  FROM internal_app_bsa_gjk.continuous_events_tag
  WHERE tag_name = 'app_type' AND tag_content LIKE '%OpenSSH%'
)
SELECT count(0)
FROM internal_app_bsa_gjk.continuous_events ce
JOIN ssh_events se ON ce.event_id = se.event_id
WHERE ce.end_time >= ... AND ce.end_time <= ...
  AND ce.judge_status IN (0, 1)
  AND ce.up_bytesall >= 104857600
  AND EXISTS (
    SELECT 1 FROM internal_app_bsa_gjk.continuous_events_tag ct
    WHERE ct.event_id = ce.event_id
      AND ct.tag_type = 0 AND ct.tag_name = 'long_connection'
  );
```

## 问题四：netflow_alert_5min 611GB 空间治理（已完成 pg_repack，转向 ES 迁移）

### 现象与约束

- 表总占用 611GB（`pg_total_relation_size` 已含 TOAST 439GB），磁盘仅剩 600GB；
- 数据保留要求 1 年以上，**不能删行**；`flow_logs`（text）数据**不能丢**；
- 每天约 +100 万 INSERT / -60 万 DELETE（净增 ~40 万/天），表未分区。

### 诊断过程与关键结论

| 步骤 | 结果 |
|------|------|
| 手动 `VACUUM ANALYZE` | 跑了 7 天完成（last_vacuum=2026-08-12），**但表大小不变** |
| 主表 dead tuple | 810 万 / 1.42 亿 live，dead_pct ≈ **5.7%**（正常） |
| TOAST 表 dead tuple | 900 万 / 2.05 亿 live，dead_pct ≈ **4.4%**（正常） |
| pg_repack 空间评估 | 需 700-800GB 临时空间，**当前 600GB 不够** |

**核心结论：空间不是膨胀（bloat）造成的，是真实数据量。** dead tuple 占比仅 ~5%，即使全部清理也只能回收 ~30GB。调 autovacuum 参数、VACUUM、repack 都无法显著瘦身——VACUUM 只把 dead tuple 标记为可复用，**不把空间还给操作系统**。

### 主表 vs TOAST 行数差异（非异常）

主表 1.42 亿行 vs TOAST 2.05 亿行（1.44 倍）是正常的：flow_logs text 超过 ~2KB 会被切成多个 TOAST chunk 存储，平均每行占 1.44 个 chunk；dead tuple 比例不一致则源于"UPDATE 不改 flow_logs 时只产生主表 dead tuple（TOAST chunk 复用）"。

### 已执行：pg_repack 在线重建（效果有限）

诊断后仍然选择对表执行 pg_repack（此前对 alert_push_dispose、session_port 有成功经验），**已执行完成**：

| 指标 | repack 前 | repack 后 |
|------|-----------|-----------|
| 表总占用 | 611 GB | **562 GB** |
| 释放空间 | — | ~49 GB |

结果与诊断预期一致：dead tuple 只占 ~5%（约 30GB 碎片），repack 把这部分碎片压实并归还 OS，但对 400+GB 的真实数据无能为力，**回收幅度有限（约 8%）**。这再次验证了"空间瓶颈在数据量本身，不在碎片"的结论。

### 最终决策：迁移至 Elasticsearch（已启动开发）

由于 PG 侧继续减空间的空间已到极限（不能删行、flow_logs 不能丢、PG 9.6 无分区），最终方案确定为**将该表整体迁移至 ES**，利用 ES 按索引生命周期管理（ILM）滚动删除老索引、天然按时间分片的优势，从根本上解决"1 年数据保留 + 持续膨胀"的矛盾。

- **当前状态**：迁移开发已启动
- **迁移收益**：flow_logs 大字段场景与 ES 的 inverted index + doc values 存储更匹配；老数据随索引过期自动释放，不再依赖 VACUUM/repack
- **迁移关注点**（待迁移方案细化）：
  - 数据回填：1 亿+ 行历史数据的批量导入速率与磁盘 IO 压力
  - 双写/双读过渡期的一致性保障
  - 查询口径对齐：PG 侧基于 end_time/judge_status/bytes 的过滤与聚合逻辑在 ES 中的等价实现
  - PG 侧退役节奏：迁移完成后原表清理/归档策略

## 问题五：列表查询 `COUNT(*) OVER()` 导致 24.5 秒（窗口函数阻止 Limit 下推）

### 现象

同一列表查询，三种写法耗时差异巨大：

| 查询场景 | 耗时 |
|----------|------|
| 列表查询（带 `COUNT(*) OVER()`） | **24.5 秒** |
| 列表查询（不带 COUNT） | **4 ms** |
| 单独 COUNT 查询 | **6.8 秒**（见问题六） |

### 根因分析

`COUNT(*) OVER()` 是窗口函数，语义要求**对整个结果集计算聚合**，优化器无法将 LIMIT 下推到扫描节点——Index Scan 必须扫完所有匹配行（76 万行）才能继续，而普通 `ORDER BY ... LIMIT 50` 找到 50 行立即停止：

```
-- 带 COUNT：Index Scan 扫 76.3 万行（线上 23 秒）
WindowAgg → Index Scan (rows=763,909)

-- 不带 COUNT：Index Scan 扫 50 行就停（0.35 ms）
Limit → Index Scan (rows=50)
```

窗口函数本身只花 0.07 ms，**它迫使前置 Index Scan 做全量扫描才是 24 秒的根源**。

叠加的第二层问题：该查询走了 Bitmap Heap Scan，默认 `work_mem=4MB` 下候选 70.8 万行撑爆位图，**92% 退化成 lossy**（lossy=534,937），Recheck 640 万行，此节点耗时 ~22 秒。session 内 `SET work_mem = '256MB'` 验证后 lossy 归零（exact=515,616 / lossy=0），该节点降到 ~9.8 秒。

> 与问题一的对照：问题一那个 236 万候选 + 大量回表的 src_ip 查询，调 work_mem 无效；本场景 70 万候选、主要开销在 recheck 的查询，调 work_mem 有效。**work_mem 只能提升 bitmap 精度，是否有效取决于候选集规模与回表占比。**

### 优化方案

| 优先级 | 方案 | 说明 |
|--------|------|------|
| P0 | **COUNT 拆分为两次独立查询**：数据查询（LIMIT 50，走 Index Scan 提前终止）+ COUNT 查询单独跑 | 零风险纯代码改动，页面 4ms 渲染、count 数字稍后跟上 |
| P1 | Django 中 `SET LOCAL work_mem = '64MB'`（事务结束自动恢复） | 仅 Bitmap Heap Scan 场景有效 |

```python
# Django 中按查询设置 work_mem
from django.db import connection

with connection.cursor() as cursor:
    cursor.execute("SET LOCAL work_mem = '64MB'")
# 同一事务内的 ORM 查询共享该设置
```

### 效果

| 指标 | 优化前 | 预期效果 |
|------|--------|----------|
| 列表数据返回 | 24.5 秒 | **4 ms**（P0 上线后） |
| Bitmap Recheck | 640 万行（lossy 92%） | 0（work_mem 调整后，实测 22s → 9.8s） |
| COUNT 总数展示 | 同步阻塞 | 异步稍后返回（用户无感） |

状态：方案已明确，**待上线验证**。

## 问题六：纯 COUNT 查询 6.8 秒——Index Only Scan 遭遇 VM 大面积失效

### 现象

单独的 count 查询走 `idx_ce_default_count_time` 的 Index Only Scan（索引已覆盖全部 WHERE 列，理论上免回表），实际耗时 **6.8 秒**：

```
Index Only Scan using idx_ce_default_count_time
  rows=752,183
  Heap Fetches: 5,330,090    ← 533 万次回表检查！
```

### 根因分析

**Visibility Map（VM）是页级粒度**：只要页中有一行不可见（存在 dead tuple），整页的"全部可见"标记就失效，Index Only Scan 扫到该页的索引条目就必须回表检查。

这张表的结构放大了问题：

| 指标 | 数值 |
|------|------|
| 表大小 | 47 GB，41 列，每行 ~1.3KB（含元组头/对齐填充） |
| 每页 8KB 能放 | 仅 5-6 行 |
| 每天 UPDATE | 40 万行（定时任务每 10 分钟批量更新 ~1 万行） |
| dead tuple 占比 | 仅 2.3%（VACUUM 在正常清理） |

**死循环**：40 万行/天 UPDATE 波及大量数据页（每页只放 5-6 行）→ 即使每天 VACUUM 一次，两次 VACUUM 之间累积的 dead tuple 已让大量页的 VM 失效 → Index Only Scan 永远要回表 → COUNT 降不下来。

> **关键认知：问题不是死元组堆积，而是 VACUUM 频率跟不上 UPDATE 节奏。** 且 VM 失效的页数 = UPDATE 触及的独立页数（40 万次 UPDATE ≈ 40 万个页），**不受行宽影响**——拆表并不减少 VM 失效页数（窄表失效比例甚至更高）。

### 优化方案：垂直拆分 + VACUUM 提频

**拆走/删除字段**：

| 操作 | 字段 | 原因 |
|------|------|------|
| 删除 | `src_info`, `dst_info`, `src_threat_mark`, `dst_threat_mark`, `iot_tag`, `key_service_tag`, `key_unit_tag`, `app_type` | 已废弃不用 |
| 拆到明细表 | `related_alerts`, `judge_info`, `judge_file`, `src_com`, `dst_com`, `src_operator`, `dst_operator`, `key_unit` | 列表页不展示，仅详情页需要 |

**核心逻辑（重要修正）**：拆分后 40 万行/天的 UPDATE 量不变，VM 失效页数也不变。COUNT 提速的真实机制是：

1. **索引从 ~1.5GB 缩到 ~400MB**——扫 75 万条索引条目的 IO 量减少 3-4 倍；
2. **shared_buffers 缓存命中率飙升**——8GB 主表几乎全缓存，Heap Fetch 从磁盘随机读（10ms/次）变内存读（0.01ms/次），差 1000 倍；
3. **VACUUM 跑得更快**——8GB 表 VACUUM 仅 1-2 分钟，可提频到每 4-6 小时一次，VM 失效窗口从 24h 缩到 4h，**这才是减少 VM 失效累积的正道**。

配套动作：
- 拆分后 VACUUM 提频（每天 1 次 → 每 4-6 小时 1 次）；
- 关键列提高采样精度：`ALTER TABLE ... ALTER COLUMN judge_status SET STATISTICS 1000;`（end_time 同理），大批量 UPDATE 后手动 ANALYZE。

### 效果（预期，待执行）

| 指标 | 拆分前 | 拆分后预期 |
|------|--------|-----------|
| 主表大小 | 47 GB | ~8 GB |
| shared_buffers 缓存率 | ~15% | ~80%+ |
| Heap Fetch 单次成本 | 10ms（磁盘） | 0.01ms（内存） |
| VACUUM 耗时 | 8-15 分钟 | 1-2 分钟（可提频 4-6 次/天） |
| COUNT 耗时 | 6.8 秒 | **< 200 ms** |

风险：中等。`VACUUM FULL` 回收空间需短暂锁表（安排窗口期，或用 pg_repack）；详情页查询加一次 JOIN（走 PK 索引，微秒级）。

### 补充：dst_ip 索引缺失（待办）

问题一已为 `src_ip` 建了单列索引 `idx_ce_src_ip`（41s → 382ms）。分析中发现 `dst_ip` 同样不在任何索引里，带 `dst_ip` 筛选的查询存在同样问题，需补充：

```sql
CREATE INDEX CONCURRENTLY idx_ce_dst_ip
ON internal_app_bsa_gjk.continuous_events (dst_ip);
```

（沿用问题一结论：单列即可，前导列为不更新的等值列；如分析报告建议的 `(src_ip, end_time DESC, up_bytesall DESC)` 复合索引，需权衡 end_time/up_bytesall 高频更新带来的写入开销，此前已评估单列方案更优。）

## 问题七：高频更新大表的系统性优化点清单（8 项）

> 除前六个独立复盘的优化点外，梳理出的其他优化项。其中一部分是已落地的实践，一部分是待推进的治理规划。

### 7.1 events / tag / port 三张表死亡行增长过快，清理不及时

**现象与根因**：三张表都是高频更新表（归并任务持续更新 `end_time`、`up_bytesall`、`down_bytesall` 等字段），每天产生大量 dead tuple；默认 autovacuum `scale_factor=0.2` 对大表意味着数百万死元组才触发一次，清理节奏远跟不上 UPDATE 节奏（连续性问题六的死循环即由此而来）。

**方案**：对三张表设置表级 autovacuum 参数，降低触发门槛并放开清理吞吐：

```sql
ALTER TABLE internal_app_bsa_gjk.continuous_events SET (
```

### 7.2 events 表大字段 + 频繁更新的叠加问题

**现象与根因**：`continuous_events` 41 列宽表（47GB）中含 TOAST 大字段，归并任务每 10 分钟批量 UPDATE ~1 万行。高频 UPDATE 与大字段叠加放大三个代价：① 每次行更新所有索引条目都要"删旧插新"；② 大字段使行宽大、每页行数少，UPDATE 污染的页数最大化；③ 大字段行更新时 TOAST chunk 复用不稳定，TOAST 侧也可能产生 dead tuple。

**方案**：垂直拆分（与问题六同一方案）——删 8 个废弃字段、拆 8 个详情字段到明细表，主表 47GB → ~8GB；配合 VACUUM 提频到每 4-6 小时。

**状态**：✅ 已完成（垂直拆分已执行，见问题六）。

### 7.3 无效更新逻辑（更新值与原值相同仍执行 UPDATE）

**现象与根因**：部分业务代码无条件执行 UPDATE，即使新值与原值一致。PG 的 MVCC 机制下**值相同的 UPDATE 同样产生新版本行**——旧行变 dead tuple、所有索引条目删旧插新、VM 失效、WAL 照写。无效更新对写入饱和的 vdb 盘是纯浪费的 IO。

**方案**：代码层治理，两种手段：

1. 更新前先做变更检测（读出旧值比对，无变化则跳过 UPDATE）；
2. 或在 UPDATE 语句加条件，让值未变的行"空更新"：

```sql
UPDATE continuous_events
SET end_time = %s, up_bytesall = %s, ...
WHERE event_id = %s
  AND (end_time, up_bytesall, ...) IS DISTINCT FROM (%s, %s, ...);
-- 值未变的行不匹配 WHERE，不产生 dead tuple
```

**状态**：📋 待代码层排查落实（重点排查归并任务和定时任务的 UPDATE 路径）。

### 7.4 VACUUM FULL 锁表 → 引入 pg_repack

**现象与根因**：`VACUUM FULL` 物理重写整张表，全程持有 `ACCESS EXCLUSIVE` 锁——期间连 SELECT 都不行。生产环境不能停业务，VACUUM FULL 不可用；普通 VACUUM 又不还空间给 OS。

**方案**：pg_repack 在线重建——建影子表 → 拷数据 → 触发器捕获增量 → swap 表名，全程不锁表。

**状态**：✅ 已多次落地（alert_push_dispose、session_port、netflow_alert_5min 均执行过；netflow_alert_5min 611GB → 562GB，见问题四）。代价是需评估临时磁盘空间（约表大小 + WAL + 排序文件）。

### 7.5 无效索引评估与清理

**现象与根因**：表上历史累积的索引未必都在被使用，每个索引都在 INSERT/UPDATE 时付出维护代价（这张表写入已是瓶颈，索引维护直接吃 IO）。已建索引中存在低使用率索引。

**方案**：用 `pg_stat_user_tables` 的索引使用统计（`idx_scan`/`idx_tup_read`/`idx_tup_fetch`）+ 索引大小做评估矩阵，对长期 `idx_scan` 极低的索引确认无业务依赖后 `DROP INDEX CONCURRENTLY`。评估前须观察完整业务周期（周报/月报类查询可能低频但必要）。

```sql
SELECT indexrelname, idx_scan, idx_tup_read, idx_tup_fetch,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname = 'continuous_events'
ORDER BY idx_scan ASC;
```

**状态**：📋 治理推进中（`idx_ce_src_ip` 等新索引同样纳入持续观察）。

### 7.6 慢查询治理机制

**现象与根因**：慢查询是"事后救火"模式——业务反馈卡顿后才逐个分析执行计划，缺乏系统性发现与跟踪机制。本周期 6 个问题全部来自事后排查。

**方案**：建立慢查询治理闭环：

1. **采集**：启用/确认 `pg_stat_statements`，按 `mean_exec_time`、`total_exec_time`（PG 9.6 为 `total_time`/`mean_time`）定期导出 Top N 慢查询；
2. **阈值告警**：对 `mean_time` 超阈值（如 1s）的查询模式登记跟踪；
3. **规范化排查流程**：`EXPLAIN (ANALYZE, BUFFERS)` → 候选行数 → lossy/Filter/Heap Fetches → 索引/改写/缓存分级处理；
4. **周期复盘**：与本优化记录文档联动，新问题按同一格式归档。

**状态**：📋 待建立（优先级建议提升——这是发现问题的前置基础设施）。

### 7.7 port 表高频更新 → Redis 缓存

**现象与根因**：port 表更新频率很高，但属于**边缘业务**——数据的实时一致性要求低，直接高频打数据库的代价（dead tuple、索引维护、IO）与业务价值不匹配。

**方案**：引入 Redis 缓存层承接高频更新，DB 侧降频落库（定时批量刷库 / 写时更新缓存 + 异步持久化）。需评估：缓存失效策略、Redis 与 DB 一致性窗口、故障时降级路径。

### 7.8 归并脚本大批量查询 netflow_alert_5min 慢 → 分批查询

## 附录：continuous_events 核心原理速查

> 整合自《continuous_events 性能问题分析报告》原理部分，供后续排查时直接查阅。

### A1. 问题因果链全景

```
宽表(41列/47GB) + 高频UPDATE(40万/天) + work_mem=4MB
    │
    ├──① COUNT(*) OVER() 阻止 Limit 下推 → Index Scan 必须全扫 76 万行
    │        └── 解法：拆 COUNT，数据查询 4ms，COUNT 独立跑
    │
    ├──② 47GB 表 shared_buffers 缓存率 ~15% → 每行 Heap Fetch 走磁盘 IO
    │        └── 解法：垂直拆分，主表 47GB→8GB，缓存率→80%+
    │             └── 附带收益：VACUUM 提频到每 4-6h，缩短 VM 失效窗口
    │
    ├──③ src_ip/dst_ip 不在索引中 → 带 IP 查询扫几十万行
    │        └── 解法：独立单列索引（src_ip 已建，dst_ip 待建）
    │
    └──④ Bitmap 候选行太多 + work_mem=4MB → lossy 退化 → Recheck 数百万行
             └── 解法：查询前 SET LOCAL work_mem
```

### A2. 堆表 / 数据页 / 元组

- 数据存在无序的**堆**中，每行（元组）有 23 字节元组头 + NULL bitmap + 列数据（含**对齐填充**）。41 列多类型混排时对齐浪费显著，47GB ≠ 纯数据大小；
- PG 以 **8KB 页**为 I/O 最小单位：页头 24B + 元组指针数组（向下生长）+ 空闲空间 + 元组（向上生长）；
- **每页行数 = 8000 ÷ 行宽**。本表 ~1.3KB/行 → 每页仅 5-6 行 → 全表扫描要读 ~640 万页。每页行数翻 5 倍，扫描量降到 1/5（但注意：VM 失效页数不随行宽变化，见 A4）；
- 每行有唯一物理地址 **ctid = (页号, 行偏移)**，索引叶子节点存的就是 ctid。

### A3. MVCC 与 UPDATE 的本质

- UPDATE **不修改原行**：旧行标记 `xmax`（变 dead），在堆末尾插入新版本（`xmin`=当前事务），并同步更新所有索引条目（删旧 + 插新）；
- 每天 40 万行 UPDATE = 每天 ~40 万 dead tuple：占空间、破坏 VM、污染 shared_buffers；
- 可见性判断：SELECT 时按当前事务快照比较元组的 xmin/xmax。

### A4. VACUUM 与 Visibility Map

**VACUUM 做什么**：扫描所有页 → 清理 dead tuple（空间标记可复用）→ 清理索引死条目 → **更新 VM** → 更新统计。**不缩小文件、不还空间给 OS**（需 VACUUM FULL / pg_repack）。

**autovacuum 触发条件**：`dead_tup >= threshold + scale_factor × live_tup`。默认 scale_factor=0.2 → 本表需 **~770 万死元组**才自动触发（按 40 万/天要 19 天），所以依赖手动定时 VACUUM——但每天 1 次仍会在两次之间累积 40 万死元组，VM 大面积失效。

**VM 机制**：独立 `_vm` 文件，每页 2 bit（bit0=全部可见 / bit1=全部冻结），**页级粒度**。页内只要有一行不可见，该页索引条目就必须回表。

**为什么每天 VACUUM 仍不够**：VACUUM 跑完时 VM 全恢复 → 10 分钟后定时任务 UPDATE 1 万行 → 1 万个页 VM 失效 → 24h 累积 40 万页失效 → 下次 VACUUM 前 Index Only Scan 全部回表。

**行宽对 VM 的真实影响**：40 万次 UPDATE = 40 万个独立页被污染，与每页放几行无关。窄表（页少）VM 失效**比例**反而更高；真正的改善来自表变小后缓存命中率上升 + VACUUM 可提频。

### A5. 索引扫描方式对比

| 扫描方式 | IO 模式 | 启动延迟 | 能否提前终止 | 适合场景 |
|---|---|---|---|---|
| Index Scan | 随机 IO | 低（首行即出） | ✅（配合 LIMIT） | 极小结果集 |
| Index Only Scan | 随机 IO（不读堆表） | 低 | ✅ | 小结果集 + VM 有效 |
| Bitmap Heap Scan | 顺序 IO | 高（等全部收集完） | ❌ | 中等结果集 |
| Sequential Scan | 顺序 IO | 低 | 不适用 | 大结果集 |

- **Index Scan**：按索引序逐条回表，叶子节点双向链表支持 ORDER BY 免排序，LIMIT 可提前终止；
- **Index Only Scan 两个前提**：① SELECT 列全在索引中；② 页在 VM 中"全部可见"。任一不满足 → Heap Fetch（本表 533 万次的来源）；
- **Bitmap**：先收集全部 ctid 进位图 → 按页号排序读 heap（随机 IO 变顺序 IO）。位图超 work_mem → **lossy 退化**（只记页号不记行号，整页读 + 逐行 recheck）；
- 优化器按估算行数选择：极小 → Index Scan；千~十万 → Bitmap；数十万以上 → Seq Scan。

### A6. B-tree 要点

- 根/内部节点存键值范围+指针，叶子节点存**键值 + ctid**，叶子间双向链表；
- `WHERE end_time BETWEEN ... ORDER BY end_time DESC LIMIT 50`：从根定位到范围起点 → 顺链表读 → 够 50 行即停（这就是 Index Scan 只扫 50 行的原因）；
- B-tree 深度 O(log n)，3856 万行的表通常 3-4 层，等值查找只需读 3-4 个页。

### A7. Limit 下推规则

| 操作 | 是否阻止下推 | 原因 |
|---|---|---|
| `ORDER BY + LIMIT` | 否 | 索引序输出，天然支持提前终止 |
| `DISTINCT` / `GROUP BY` / `HAVING` | 是 | 需要全量输入比较/聚合 |
| `UNION / INTERSECT` | 是 | 集合操作需全量结果 |
| **`COUNT(*) OVER()` 等窗口函数** | **是** | 窗口语义要求对整个 partition 计算，扫到 50 行停会导致 COUNT 值错误 |

### A8. TOAST

- 行数据超 ~2KB 时大字段迁到独立 TOAST 表（切 2KB chunk）；SELECT 大字段需多一跳 TOAST 读取；
- 四种策略：PLAIN（不压缩不 TOAST）/ **EXTENDED（默认：先压缩再 TOAST）** / EXTERNAL（不压缩）/ MAIN；
- 列表页 `SELECT *` 若含 TOAST 字段，即使只返回 50 行也带来额外 TOAST IO；TOAST 表有自己的 VM，同样会失效。

### A9. work_mem 与 shared_buffers

**work_mem 是 per-operation**：一条 SQL 内 Sort / Hash / Bitmap 各消耗一份，总消耗可能是 N × work_mem。

| 值 | Bitmap 行为 | 并发风险 |
|---|---|---|
| 4MB（默认） | 70 万行候选 → lossy | 低 |
| 64MB | 70 万行 → exact | 中（×10 并发 = 640MB） |
| 256MB | 百万行 → exact | 高（×10 并发 = 2.5GB） |

最佳实践：`SET LOCAL`（事务结束自动释放）、先 EXPLAIN 确认存在 Bitmap/Sort/Hash 节点再调。

**shared_buffers**：全连接共享的页缓存。47GB 表 + 4-16GB 缓存 → 命中率仅 ~15%，大量 Heap Fetch 走磁盘（10ms/次）；8GB 表几乎全缓存，Fetch 变内存读（0.01ms/次）。可用 `pg_prewarm` 预热热点索引。

### A10. 执行计划节点速查（慢的标志）

| 节点 | 慢的标志 |
|---|---|
| Index Only Scan | **Heap Fetches 大**（VM 失效） |
| Bitmap Heap Scan | **lossy + Recheck 大** |
| WindowAgg | 本身快，但**阻止下层提前终止** |
| Sort / HashAggregate | external merge / Batches > 1（溢出磁盘） |
| Nested Loop | 外表行数 × 内表查找耗时 |
| Limit | 无法下推时等价于没加 |

### A11. pg_stats 统计信息

优化器靠 `pg_stats` 估算行数选计划。`rows=7 估算 vs 61 实际` 这类偏差来自：上次 ANALYZE 后大量变更、默认采样 `default_statistics_target=100` 不够、缺多列扩展统计。高频变更表要定期 ANALYZE + 对关键列 `SET STATISTICS 1000`。

### A12. 常用 SQL 速查

```sql
-- 表统计信息
SELECT n_live_tup, n_dead_tup, last_vacuum, last_autovacuum,
       pg_size_pretty(pg_total_relation_size('continuous_events')) AS total_size
FROM pg_stat_user_tables WHERE relname = 'continuous_events';

-- 每列平均宽度（评估拆分收益）
SELECT a.attname, coalesce(s.avg_width, 0) AS avg_bytes
FROM pg_class c
JOIN pg_attribute a ON a.attrelid = c.oid
LEFT JOIN pg_stats s ON s.tablename = c.relname AND s.attname = a.attname
WHERE c.relname = 'continuous_events' AND a.attnum > 0 AND NOT a.attisdropped
ORDER BY avg_bytes DESC;

-- 事务级 work_mem
SET LOCAL work_mem = '64MB';

-- 不锁表建索引
CREATE INDEX CONCURRENTLY idx_ce_dst_ip
ON internal_app_bsa_gjk.continuous_events (dst_ip);
```
